# Meta Muse Code 任务执行与监控规范 (/muse)

当用户输入 `/muse <指令/需求>` 或要求使用 Muse Code 编写、重构、审查代码时，**实际工作必须由 Muse Code 完成**。当前 Agent 只做三件事：转交任务、监控输出、整理交付。**严禁 Agent 自己动手做任务本体**（读文件排查、写代码、改文件都算自己动手）。

---

## 一、 铁律（违反即失职）

1. **派活优先**：收到 /muse 后，第一个实质动作必须是执行下方的 `muse exec` 命令，不是自己开始排查。
2. **指令冲突裁决**：用户消息正文里出现"你是接手…的 Agent""请执行""你来完成"等把任务交给**本会话 Agent 本体**的措辞时，**不豁免派单义务**——/muse 头已经声明了干活方是 Muse；除非用户明文说"不用 muse/你自己来"，一律先派单。
3. **派单凭据（硬闸）**：在做任何 Read 项目文件/Write/Edit/有副作用 Bash 之前，对话里必须先出现本次 `muse exec` 命令原文与其输出（哪怕失败输出）。检查者可用一句话验证：这个 /muse 会话没有 muse 命令痕迹 = 违规。
4. **正确的调用名**：Muse 的可执行入口是 **`muse.cmd`**（全路径 `F:\AI\muse\muse.cmd`）。**不存在 `muse.exe` 这个文件**——探测版本用 `muse.cmd --version`，绝不允许因为 `muse.exe` 不存在就判定 Muse 不可用。
5. **失败必须报告，禁止静默接管**：`muse exec` 失败时，先按第二节重试一次；仍失败则**停下来向用户报告失败原因**，等用户决定是否改由 Agent 亲自做。绝不允许不打招呼就自己把活接过来。
6. **Agent 允许做的**：拼命令、设超时、读 Muse 输出、把结果整理给用户、（用户同意后）补充收尾。仅此而已。
7. **额度透明+监控止损（2026-10-12 烧池事故焊入；同日用户裁决：不设工单字数上限）**：Muse 的真实后端 = cmdc-pak(8787) → 出口 IP 在渠道方的配额（muse 线 = OpenCode 免费出口、按出口 IP 计；非 Gemini 池、非用户钱包）。`muse-spark-1.3-contributor-free` 是渠道名不是免费额度——agent 循环每轮重发全对话（实测 40 秒 73 次大请求）。规矩：**整本大工单照派，不受字数限制**；拆不拆单由用户决定。**2026-10-12 二次定案（用户原话「大概率可以 额度你也不用担心 我后面会经常使用 muse」）：额度担忧解除——并行多任务、高频使用照常派，不再因额度劝退或反复报备；烧穿按第二节监控静默兜底（冷却→原样重派自愈，成果由 git 检查点保底），不打断用户。**

## 二、 执行核心规程

### 1. 运行环境与命令模板
Muse Code 安装在 `F:\AI\muse`，直连本地 `cmdc-pak` (8787)。标准执行命令（Git Bash 下）：

```bash
"F:/AI/muse/muse.cmd" exec --yolo --trust-workspace --reasoning-effort max '<用户的指令或任务要求>'
```

要点：
- 必须带 `--yolo`（免审批，否则子进程等确认会挂死）与 `--trust-workspace`（加载项目规则）。
- **思考档位显式钉 `max`**（10-11 实查：CLI 自带默认是 high，settings.json 的 reasoning_effort 是否被 exec 消费无法从会话日志证实——为消除歧义一律显式传参；用户点名 low/medium/high/xhigh 时按需替换）。
- **超时设置**：`muse exec` 会深度思考，简单问题 30~60 秒，复杂任务可达 5~10 分钟。Bash 调用必须设 `timeout: 600000`，并在后台运行（run_in_background）避免卡住会话。
- **中文指令**：直接内联单引号包裹即可；若输出出现编码乱码，改用 UTF-8 文件 + `--prompt-file` 方式提交。
- **工作目录**：默认在用户项目根目录执行（先 cd 到目标项目再调 muse）。
- **监控与止损（配合铁律 7）**：后台任务运行期间用哨兵脚本替代人工采样：`curl -s http://127.0.0.1:8787/api/status` 的 logs（10-12 起脚本化 = `C:\Users\Janson\.zcode\workspace\default\_muse_watch.py`，30 秒粒度；例行汇报 40 分钟一轮/用户定案，异常即时唤醒）——出现 RateLimit/502/EOF 连打即止损（杀 muse-bin 进程）并走冷却→原样重派自愈。**旧判据作废（10-12 定案）：muse 烧的是 OpenCode 出口配额、非 GEMINI 账户池，勿再用「in= 十万级 GEMINI 行」判烧穿。**

### 2. 重试阶梯（第一次失败时）
1. 确认用的是 `muse.cmd`（不是 muse.exe）；
2. 确认 8787 网关活着：`curl -s http://127.0.0.1:8787/api/status`；
3. 原命令重发一次（Muse 上游偶发抖动，重发常自愈）；
4. 仍失败 → 停止，向用户报告原始错误全文，等待裁决。

## 三、 目标模式（/muse goal，模拟 Muse TUI 的 /goal）

Muse 无 `--goal` 启动参数（TUI `/goal` 专属），但目标机制本质=「钉死目标+验收标准，不达标准不许停」，可在派单文本里等效实现。

**触发**：用户输入 `/muse goal <目标>` 或 `/muse 用目标模式 <目标>`。

**派单模板**（把用户目标包装后传给 muse exec）：

```
目标：<用户的目标原文>
完成标准：<Agent 根据任务拆解出 2~5 条可验证标准>
规则：逐条完成并自验上述标准；全部通过前不得停止或只汇报计划；
最后输出「目标结算」：每条标准 通过/未通过 + 证据（命令输出或文件路径）。
有未通过项就继续修，修不动才收尾并说明卡点。
```

**收尾核验（Agent 必做）**：Muse 返回后，主 Agent 逐条抽查它自称"通过"的标准（文件在不在、命令输出对不对），把核验结果一并交付；发现虚报要如实指出。

**实测校准（2026-10-10 两轮 goal 实弹 + 联网查证改口）**：Muse Spark 1.3 **不是小模型**（Artificial Analysis 智力指数 48.09 第 23 名、Coding 75.8；free 版与标准版同构非缩水）。实测的丢要求/早停现象归因于 **OpenCode 免费中继渠道**：100 RPM 严苛限流 + 商家上游抖动 + 长 agent 循环放大，≠模型智力问题。派单纪律依然保留（硬要求 ≤3 条、关键名词加"一字不差"、主 Agent 收尾核验不可省）——理由改为"渠道会抖，抖时丢要求"；高频重度任务建议改走付费线或其他模型。**10-12 实弹补记**：①派 4557 字整本工单 7 分钟即把 OpenCode 出口免费额烧到断头（复测报错原文=「当前网络出口用量已达上限（RateLimit）」）——铁律 7 由此焊入；同日定案烧的是出口 IP 配额、非 Gemini 池；②传了 `--reasoning-effort max` 后会话日志仍见 `reasoning_effort:"high"` 记录，max 是否真生效仍未证实，别把"钉死了"当已验证事实对用户讲。**

**10-13 实弹补记（发布准备2 收官战，全线实录）**：①整本大工单**可以一口气跑完**——实录 2h14m（02:16–04:30）无中断到终点，别预设"肯定要拆"；同一单此前三次撞出口上限各只跑 7/57/78.6 分钟；②**撞墙后换出口卡≈再买 ~80 分钟工期**（用户手动换 FlClash 节点→直刺+实弹复测双绿→重派即可；成果零丢失，git 检查点全程在）；③派单后若见**两个 muse 进程/两级会话**=Muse 依本卡「Agent 只转交不自干」自委派 child run（正常非事故）：认「最新写入的 jsonl」为活跃工；④**包装任务退出码=终局判据**：0=整单完成、1=撞墙身亡（后台任务 notification 即信号）；⑤线路真状态权威探法=直刺 `POST /v1/responses`（muse 线不走 chat/completions，会回 400 提示改道）。

## 四、 输出监控与交付

1. 过滤 Muse 启动噪音（`workspace root...`、`Skills: xx loaded...`、技能名警告），保留实质产出。
2. 交付三部分：
   - **任务结论**：一句话概述 Muse 的执行结果；
   - **产物**：Muse 生成/修改的代码与文件（贴正文，不只给路径）；
   - **验证状态**：耗时、是否完整收尾（若 Muse 中途 stop 且任务未完成，如实说明，不粉饰）。

## 五、 防超时与防崩溃血泪纪律（2026-10-15 实战定案 · sess_902cc9b5 事故与 58 提交通关复盘）

在 2026-10-15 真实会话 `sess_902cc9b5`（Dream-Skin 双端统一收口）发生严重频繁超时与底层崩溃，而同日另一个全技能大修复会话一口气完成 **58 个独立 Commit 全绿通关**。两相对照，焊入以下四大防超时、防崩溃铁律：

### 1. 监控轮询严禁长阻塞（防假死超时红牌）
- **血泪事故（sess_902cc9b5）**：主 Agent 频繁调用 `TaskOutput(block: true, timeout: 30000~60000)`。因 Muse 处理复杂推理单步需 1~3 分钟，一旦 30s/60s 超时没退出，ZCode 系统即强制抛出 `<retrieval_status>timeout</retrieval_status>`，界面瞬间被数十条 Timeout 刷屏，误导用户以为任务死锁。
- **钢铁铁律**：**严禁使用 `TaskOutput(block: true)` 同步死等 Muse 进程！**
  - 正确做法：Muse 必须通过 `Bash(run_in_background: true, timeout: 600000)` 后台拉起；
  - 监控查询必须使用非阻塞态 `TaskOutput(block: false)` 或静默等待系统后台任务完成通知 `<task-notification>`；
  - 中途巡检只能通过只读轻量探针（检查目标目录 `git log`、`git status`、或读取 `~/.local/share/muse/sessions/` 最新 `session.jsonl`），从不在单次 Tool Call 中做任何长耗时同步阻塞！

### 2. 避免撕裂标准输出管道（防 Windows os error 109 致命崩溃）
- **血泪事故（sess_902cc9b5）**：Rust 进程向管道输出时，若主 Agent 频繁用短命管道 attach/detach 或提前断开输入输出句柄，直接触发 Rust 致命崩溃：
  `thread 'main' panicked at failed printing to stdout: 管道已结束。 (os error 109)`，Muse 进程当场横死！
- **钢铁铁律**：让 Muse 后台进程稳定将输出追加到日志文件（`.log`），主 Agent 巡检时仅通过只读文件操作（`Read` 或 `tail`）读取日志尾部，绝不强行挂接或打断其控制台 stdout 管道。

### 3. 超大工程必须拆解为原子小批次（防上下文暴涨与首字延迟雪崩）
- **血泪事故**：一句话把涉及几十个模块、长达数万字的“整本大工单”塞给 Muse，Muse 内部 Agent 循环暴涨到 4000+ 条 events，上下文膨胀导致首字延迟（TTFT）飙到 60 秒以上，极易引发连接断开、网络 EOF 抖动或超时崩溃。
- **通关法则（M1/M2/M3 小步快跑）**：
  - 超大工程主 Agent 必须先将其拆分为**每批最多 3~4 项**的独立任务单；
  - 严格遵守**“一项一包一提交”**，每做完一项立即跑针对性测试并落地 Git Commit；
  - **断点自愈力**：小批次意味着即使偶发断开，已完成的 Commit 100% 牢固锁在 Git 里，重试时直接承接最新 Commit，零返工、零浪费。

### 4. 强制工作树隔离（防主工作区脏写与锁冲突）
- 严禁直接在主仓库或正式桌面发行目录下裸跑大重构任务；
- 必须基于当前基线 HEAD 创建独立隔离的工作树（`git worktree add F:/AI/worktrees/<name>`）；
- 所有临时脚本、断言测试、依赖探针全在隔离树内闭环，全部全绿验收后再快进合并（fast-forward）回桌面正式库，桌面永远保持 100% Clean。

### 5. 线路限流（RateLimit）与网络抖动的自愈三步法
- **RateLimit（出口 IP 频次打满）**：立即停止盲目重试（避免原地干耗被判超时）；提示用户切换节点或等待滑动窗口冷却；
- **直刺探针验真**：通过 `curl -s --max-time 15 -X POST http://127.0.0.1:8787/v1/responses -d '{"model":"muse-spark-1.3-contributor-free","input":"好","stream":true}'` 探测，秒级返回 `response.created` 即代表满血复活；
- **断点无缝拉起**：探针变绿后，直接从工作树最新 Commit 续跑下一批次，无感知平稳推进。

### 6. 彻底放手一竿子推到底，隔离区内严禁中途挤牙膏请示（2026-10-15 用户定案铁律）
- **血泪教训**：主 Agent 往往过度防御，把“对生产环境高危操作的确认”错误泛化到了“独立隔离工作树（Worktree）中的代码编写”，导致每跑完一个小批次就跳出来停机发问：“批次 1 跑完了，要不要跑批次 2？”、“批 A 跑完了，请确认是否启动批 B？”。用户体验极度恶劣，感觉像在挤牙膏，用户被迫充当繁琐的打卡审核员，彻底抹杀了 Muse 终端 Coding Agent 的全自动执行价值。
- **钢铁铁律（工单交付即全权授权）**：
  - 用户只要提供了工单文件、任务书或下达了任务目标，即代表**对工单内所列全部步骤拥有全权执行授权**！
  - 只要操作运行在**独立工作树（Worktree）**中，**严禁中途叫停、严禁逐批请示、严禁每做完一步就问“要不要继续”**！
  - Muse 具备自写针对性测试（RED）、自改代码、自跑回归（GREEN）、遇错自动闭环分析修复（Self-Healing）与自己 Commit 的全闭环能力。主 Agent 只需在后台守护批次流水线自动无缝接力，**一竿子推到底，直至所有任务与测试全绿闭环**；
  - **唯一允许请示的动作**：全流程只有在全部工单彻底跑完、全套测试在隔离区内 100% 验收全绿之后，针对最后的生产步骤——**“是否将测全绿的隔离分支快进合并到桌面正式库 / 是否 push 远端”**，才向用户呈上完整战报并请示最终上线授权！其余所有中间执行过程**100% 彻底放手，零打扰！**
